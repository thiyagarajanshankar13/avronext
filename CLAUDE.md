# AvroNext

Stateless Next.js 15 (App Router) front end for Nextcloud: Projects = Deck, Spaces = Collectives. See README.md for features, env vars and the Nextcloud mapping.

## Rules

- **No storage.** No database, no files, no server-side cache beyond React `cache()` per request. The only state is the encrypted session cookie (`lib/session.ts`), the short-lived Login Flow cookie and the theme cookie. Don't add persistence; anything that must be remembered belongs in Nextcloud.
- **`src/lib/nextcloud/` is the only code that calls Nextcloud.** Pages/actions go through it. Deck uses its REST API (`/index.php/apps/deck/api/v1.0`, needs `OCS-APIRequest: true`) plus OCS for comments; Collectives uses OCS (`/ocs/v2.php/apps/collectives/api/v1.0`); page bodies are Markdown files read/written over WebDAV (`pageFile()`).
- **Reads** happen in server components via `lib/loaders.ts` / `lib/workspace.ts` wrapped in `loadOrSignOut` (a 401 → `/logout?expired=1`, because cookies can't be changed while rendering). **Writes** are server actions (`app/(app)/projects/actions.ts`, `app/(app)/spaces/actions.ts`, `app/(app)/files/actions.ts`) wrapped in `run()` from `lib/actions.ts`, which returns `{ ok, data | error }`. See "Writes that move to another screen" below for which actions may revalidate.
- Deck's card update endpoint needs the whole card (title, type, owner, …): use `updateCard()`, which reads it first. Boards created through the API have no stacks; `createProject` adds them.
- **Markdown** is rendered by `lib/markdown.ts` and must be sanitised: `markdown.server.ts` (sanitize-html) in server components, `useMarkdownHtml()` from `markdown.client.ts` (DOMPurify, needs the DOM, so it's empty until mounted) in client components. Both share one allow-list.
- File proxying (`/api/files`) serves images inline (plus PDFs and audio/video with `?view`, for the Files viewer), everything else as a download, with a sandbox CSP (PDFs inline excepted: the browser's PDF viewer won't run sandboxed).
- **Navigation and freshness.** Every `<Link>` has `prefetch={false}`: Next's prefetch cache keeps a copy of a page and would show it from before the user's own edits. There are no `loading.tsx` files: with loading boundaries, a navigation that interrupts another (or follows a server action) can leave the router stuck on the old screen in this Next.js version. Instant feedback comes from `components/NavProgress.tsx` (top bar + fade). Streaming *inside* a page with `<Suspense>` is fine (Your work, search).
- **Writes that move to another screen** (create, save, trash, archive) return data, and the client calls `useGoFresh()(href)`, which navigates and then refreshes once arrived. Don't `redirect()` or `revalidatePath()` in those actions or call `router.refresh()` right after `router.push()`: they race the navigation. Actions that stay on the page may `revalidatePath`.
- **The board owns its state** (`components/project/useBoard.ts`): optimistic updates, no adopting of later server renders; fresh data via `reload()` (column changes, tab refocus) or the `ISSUE_CREATED` event. Issue open/close only touches browser history (`useIssueParam`). Columns are reordered by dragging their header or via the column menu (`moveColumn` → `reorderColumns`, which renumbers Deck stack `order` 0…n; managers only). The label filter is shared state (`boardFilterContext.ts`, a small in-memory store): the filter bar's Label menu, the project sidebar's Labels list (published by the mounted board/list with issue counts; labels with no issues are hidden there unless selected) and the top-nav Create dialog's prefill all read and write it; it survives Board ↔ List and resets when another project opens.
- **Attachments** go through route handlers in `app/api/attachments/` (not server actions: no body-size limit, streaming). Those paths skip the middleware (it buffers and truncates big bodies), so each checks the session and `sameOrigin()` itself. Issue files are Deck v1.1 `file` attachments; page files live in `.attachments.<pageId>/` beside the page's Markdown (Nextcloud Text's convention, referenced as `![name](.attachments.<id>/name)`), uploaded with `If-None-Match: *` so nothing is overwritten. Every file the browser gets comes through `fileResponse()` in `lib/files.ts` (images inline, everything else a download, sandbox CSP); thumbnails come from Nextcloud's preview service via `/api/preview/<fileId>`. The UI is `components/attachments/` (`Attachments` panel, `useUploadQueue`, `useFileDrop`).
- **Files** (`app/(app)/files/`, `components/files/`, `lib/nextcloud/files.ts`): WebDAV PROPFIND/MOVE/COPY/DELETE/PROPPATCH + `SEARCH` (Recent) + `REPORT` (Favourites), OCS Share API for sharing. Paths are user-root relative (`/a/b`), always through `cleanPath()`. Items with mount type `collectives-user`/`collective` and dot-files are hidden everywhere (`isHiddenItem`); `/files/Collectives` redirects to `/spaces`. Views are `?view=recent|favorites|shared|sharing` (not path segments, so they can't clash with folder names). `FilesBrowser` owns its list (optimistic updates, `reload()` on the `FILES_CHANGED` event and tab refocus) and is keyed by view + path. Uploads go through `/api/upload` (skips the middleware like attachments; one request up to 10 MB, else Nextcloud chunked upload v2: `start` → `chunk` → `finish`), queued by `UploadsProvider` in the Files layout so they survive folder changes; clashes are asked once (replace / keep both / skip) in `useUploadFlow`. `/api/files?view` also serves PDFs and audio/video inline (Range passed through for seeking); other types stay downloads. The viewer's Office readers are dynamic imports (`viewer/DocxView` in a scripts-off sandboxed iframe, `SheetView` = SheetJS from its CDN tarball, `SlidesView` = our own pptx renderer: React elements only, never HTML from the file). Relative times in client components need `suppressHydrationWarning`.
- **Rich text editor** = `components/editor/` (TipTap 3 + `@tiptap/markdown`, which parses with `marked` like `lib/markdown.ts`). `extensions.ts` is the document model shared by the editor and `scripts/markdown-roundtrip.ts`: keep it to what Markdown can store (underline is off) plus `Callout` (Nextcloud's `::: info|success|warn|error`). `AttachmentImage` keeps the stored `src` exactly as written (relative `.attachments.<id>/…`) and only displays it through `resolveSrc`; non-image files embedded with image syntax show as file chips. Output goes through `tidyMarkdown()` (no `&nbsp;` for empty paragraphs, no blank-line runs). Saves only happen when `isDirty()` (Markdown differs from what the editor produced on load), so untouched pages/descriptions are never rewritten. After changing anything here run `npm run check:markdown`. In browser tests, give key presses a few ms: ProseMirror picks up native caret moves asynchronously.
- **People and admin.** Project access = Deck ACL (`lib/nextcloud/deck.ts` `addAcl`…; roles map to edit/share/manage in `projects/actions.ts`). Space access = the collective's Nextcloud team (`lib/nextcloud/teams.ts`, levels 1/4/8/9; groups/teams show as members with `basedOn.source` 2/16) plus `editLevel`/`shareLevel` on the collective. The people picker searches Nextcloud's sharees API (`lib/nextcloud/people.ts`). Administration = the provisioning API (`lib/nextcloud/admin.ts`); `getAdminScope()` (admin / sub-admin groups) decides what to show, but Nextcloud enforces everything. Group admins can't read `/cloud/groups/details`, so `listGroups()` falls back to their own groups. Admin pages check the scope themselves before loading (pages render in parallel with the layout's check). Actions refuse self-lockout (disabling/deleting yourself, removing your own admin rights, deleting the admin group).
- Styling is plain CSS with Atlassian-like tokens in `app/globals.css`. No UI kit. Dark styles hang off `:root[data-theme='dark']`, never `@media (prefers-color-scheme)`: the profile menu's Light/Dark/System switch (`ThemeSwitch`) stores the choice in the `avronext_theme` cookie (a preference, not app state), the root layout renders `data-theme` from it, and for System the inline `THEME_SCRIPT` (`lib/theme.ts`) resolves and follows the OS before first paint.

## Testing

`npm run typecheck`, `npm run check:markdown` (editor ↔ Markdown round trip) and `npm run build`. There are no browser tests in the repo yet. For UI changes, run against a real Nextcloud. A throwaway one: `docker run -d --network host -e SQLITE_DATABASE=nc -e NEXTCLOUD_ADMIN_USER=admin -e NEXTCLOUD_ADMIN_PASSWORD=admin -e NEXTCLOUD_TRUSTED_DOMAINS=localhost nextcloud:31-apache`, then install Deck and Collectives (`occ app:install deck collectives`, or extract their release tarballs into `custom_apps/` and `occ app:enable`).
